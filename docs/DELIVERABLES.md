# BedSynth AI - submission index

This index maps every item of the project brief (weekly deliverables, grading criteria, required
scenario families and objectives) to the evidence in this repository. All paths are relative to the
project root. The reports in `reports/` are generated by the pipeline scripts and are rewritten on
every run, so this index points to their sections rather than repeating numbers: headline results
are in the **Results** section of [`README.md`](../README.md) and in
[`reports/week3_evaluation.md`](../reports/week3_evaluation.md). The team's work split and
presentation parts are in [`TEAM_PLAN.md`](TEAM_PLAN.md).

## Quick route for examiners

1. [`README.md`](../README.md) - overview, setup, API usage, how validity is guaranteed, results,
   limitations.
2. `reports/week1_data_preparation.md` §1.2 - each scenario family of the brief mapped to named
   scenarios with their training support (every report opens with a Summary of its key facts).
3. `reports/week2_synthesis_pipeline.md` §3 and §5 - the SDV constraint groups and the constraint
   ablation.
4. `reports/week3_evaluation.md` §2, §3, §6 and §7 - model comparison against a real-data ceiling
   and a no-learning floor, improvements made to SDV generation (ablation, the ward_daily A/B test
   with its four-seed ranges, improvement log), optimisation-model testing, remaining quality gaps;
   the full A/B log is in DESIGN §7.2 and `reports/experiments/ward_daily_band_groups_ab.json`.
5. `reports/week4_api_system.md` §1, §2, §3 and §5 - how to run and call the generator, end-to-end
   API evidence, one generated dataset per scenario, test results (fast and slow suites).
6. [`docs/DESIGN.md`](DESIGN.md) §1.1 - background and design rationale (how the SDV synthesizers
   work, the fidelity-utility-privacy trade-off, why two single-table models).
7. Run the service (`python scripts/04_serve_api.py`) and open `http://127.0.0.1:8000/ui`;
   [`docs/API.md`](API.md) is the full API reference.
8. [`docs/presentation/BedSynth_AI.pptx`](presentation/BedSynth_AI.pptx) - the slide deck.

## 1. Reproducing the submission

Set up the virtual environment as described in the README (`python` below means the `.venv`
interpreter, `.venv\Scripts\python.exe` on Windows). `data/` and `models/` are build outputs
(listed in `.gitignore`); every one of them is regenerated by the commands below, and the
submission zip built by `scripts/package_submission.py` includes `data/processed/`, `models/` and
`data/synthetic/api_demo/`, so examiners do not have to regenerate them.

**The pipeline commands overwrite the submitted artefacts in place.** The whole pipeline and the
Week 1-4 commands below rewrite `data/processed/`, `models/` (with the registry defaults), `reports/`
(results, reports, API demo evidence, JUnit files) and `data/synthetic/api_demo/`; after a `--quick`
run they no longer match the README Results, DESIGN or the deck. To check reproducibility without
touching the submission, point the `BEDSYNTH_*_DIR` variables at a scratch folder first (README,
Quick start; `docs/DEMO_SCRIPT.md` section 6).

| Step | Command | Regenerates |
|---|---|---|
| Whole pipeline | `python scripts/run_pipeline.py` (`--quick` for a short run, `--dry-run` to list the steps with their script names and options) | prepare, train, evaluate and API demo in fresh interpreters; stops at the first failure |
| Week 1 | `python scripts/01_prepare_data.py` (`--resimulate` rebuilds `data/raw`, `--seed N`) | `data/processed/`, `reports/week1_data_preparation.md`, `reports/figures/week1_*.png` |
| Week 2 | `python scripts/02_train_synthesizers.py` (`--quick`: 10-epoch CTGAN/TVAE; `--tables`, `--experiments`) | `models/`, `models/registry.json`, `reports/week2_synthesis_pipeline.md`, `reports/figures/week2_raw_validity.png` |
| Week 3 | `python scripts/03_evaluate.py` (`--quick`; `--tables`, `--models`, `--rows`) | `reports/results/*.json`, registry default per table, `reports/week3_evaluation.md`, `reports/figures/week3_*.png` |
| Week 4 | `python scripts/05_api_demo.py --run-tests --run-slow-tests` | `reports/api_demo/`, `data/synthetic/api_demo/`, `reports/results/pytest_junit.xml` (fast suite), `reports/results/pytest_junit_slow.xml` (slow suite), `reports/week4_api_system.md`, `reports/figures/week4_api_latency.png` |
| Service | `python scripts/04_serve_api.py` (`--port 8001` if 8000 is taken), then `/ui` (offline demo UI) or `/docs` (OpenAPI) | - |
| Demo client | `python demo/demo_client.py` against the running service; `demo/requests.http` for the VS Code REST Client | - |
| Tests | `python -m pytest -m "not slow"` and `python -m pytest -m slow` | - |
| Slide deck | `node docs/presentation/build_deck.js` (after `npm ci` in `docs/presentation/`) | `docs/presentation/BedSynth_AI.pptx` from the saved results |
| Submission | `python scripts/package_submission.py` (`--dry-run` lists the files and the scan result) | `dist/BedSynth_AI_submission.zip`, written only if no home-directory path, user name or host name is found in the files |

`run_pipeline.py --run-tests --run-slow-tests` passes both test options to its demo step; without
them the demo step leaves the stored JUnit files untouched, and the Week-4 report summarises those.
The README's Quick start lists measured runtimes.

## 4. Scenario families of the brief

A scenario (`bedsynth/scenarios.py`) combines **conditions** on categorical training columns, which
the generated rows must take (served by routing to the segment models and exact pooled rejection from
their unconditional draws; DESIGN §7.3, §8.5), and **filters** on training or derived columns,
enforced by rejection sampling. Request one with `{"table": ..., "scenario": "<name>", "num_rows": ...}` on
`POST /api/v1/generate`; extra `conditions` in the request are intersected with the scenario's and
extra `filters` tighten its filters. The brief's families map to scenario categories in the code
(category ids in brackets).

| Brief family | Scenario (table) | Definition | Columns that express it | Evaluated by |
|---|---|---|---|---|
| Normal, high and low occupancy [`occupancy`] | `normal_occupancy`, `high_occupancy`, `low_occupancy` (ward_daily) | `occupancy_level` = normal / in {high, critical} / low | `occupancy_level`, `occupancy_rate`, `census_start`, `census_end`, `available_beds` | checks `occupancy_mean_by_ward`, `occupancy_distribution_by_ward`, `occupancy_band_mix_by_ward` (system check); Week 3 §8 |
| Seasonal demand [`seasonal`] | `winter_demand`, `summer_demand` (ward_daily); `winter_admissions` (patient_stays) | `month` in {12, 1, 2} / {6, 7, 8}; `admission_month` in {12, 1, 2} | `month`, `season`, `admissions_emergency`; `admission_month`, `admission_season` | `monthly_emergency_profile`, `seasonal_pressure_contrast`, `short_staffing_share_by_season` |
| Admission and discharge patterns [`patient_flow`] | `weekend_operations` (ward_daily); `emergency_admissions`, `weekend_discharges` (patient_stays) | `day_of_week` in {Sat, Sun}; `admission_source` = emergency; filter `discharge_day_of_week` in {Sat, Sun} | `day_of_week`, `admissions_emergency`, `transfers_in`, `transfers_out`, `discharges`, `discharges_before_noon`; `admission_source`, `admission_hour`, `discharge_hour`, `discharge_day_of_week`, `is_weekend_discharge` | `weekly_discharge_profile`, `weekend_weekday_discharge_ratio`, `before_noon_discharge_share`; `admission_hour_profile_by_source`, `discharge_hour_profile`, `weekend_discharge_share`, `transfer_out_share_by_ward` |
| Emergency bed requirements [`emergency`] | `emergency_pressure` (ward_daily); `long_bed_waits` (patient_stays) | high/critical occupancy + filter `emergency_boarders` >= 1; emergency admissions + filter `bed_wait_hours` >= 4 | `emergency_boarders`, `avg_bed_wait_hours`, `admissions_emergency`; `bed_wait_hours` | `boarding_prevalence_by_occupancy_band`, `relationship_occupancy_boarders`, `emergency_bed_wait_distribution`; capacity planning (p95 of `census_end + emergency_boarders`) in Week 3 §6 |
| Ward utilisation [`utilization`] | `escalation_capacity`, `reduced_capacity` (ward_daily); `long_stay_patients` (patient_stays) | high/critical occupancy + filter `escalation_beds_open` >= 1; filter `beds_closed` >= 1; filter `los_nights` >= 7 | `ward_id`, `bed_capacity`, `escalation_beds_open`, `beds_closed`, `available_beds`, `occupancy_rate`; `los_nights`, `los_days` | `relationship_escalation_occupancy`, `zero_inflated_count_shares`; `los_by_source`, `los_by_ward` |
| Scheduled procedures [`scheduling`] | `scheduled_procedures`, `elective_cancellations` (ward_daily); `elective_admissions`, `rescheduled_electives` (patient_stays) | GSUR/ORTH/CARD on weekdays + filter `elective_scheduled` >= 2; filter `elective_cancelled` >= 1; `admission_source` = elective (+ filter `times_rescheduled` >= 1) | `elective_scheduled`, `elective_cancelled`, `admissions_elective`, `elective_cancellation_rate`; `booking_lead_days`, `times_rescheduled`, `admission_day_of_week` | Week 3 §5: `weekly_elective_profile`, `relationship_bed_pressure_cancellations`, `elective_lead_time_distribution`, `elective_reschedule_share`, `relationship_lead_reschedules`, `elective_admission_weekday_profile`, `elective_admission_window_share`; booking-quota decision in Week 3 §6 |
| Bed turnover [`turnover`] | `high_turnover` (ward_daily); `slow_bed_turnaround` (patient_stays) | six inpatient wards (not AMU or PAED) + filter `bed_turnover_rate` >= 0.30; filter `bed_turnaround_minutes` >= 180 | `bed_turnover_rate` = (`discharges` + `transfers_out`) / `available_beds`, `avg_bed_turnaround_min`; `bed_turnaround_minutes` | `relationship_census_discharges`, `bed_turnaround_distribution` |
| Delayed discharge [`delayed_discharge`] | `delayed_discharge_pressure` (ward_daily); `delayed_discharge_stays` (patient_stays) | filter `delayed_discharge_rate` >= 0.15; `delay_reason` other than none + filter `discharge_delay_hours` >= 4 | `delayed_discharges`, `delayed_discharge_rate`; `delay_reason`, `discharge_delay_hours`, `discharge_destination`, `is_delayed_discharge` | `relationship_delays_occupancy`, `delay_prevalence_by_destination`, `mean_delay_by_reason` |
| Varying staffing or scheduling [`staffing`, `scheduling`] | `staffing_shortage`, `staffing_surplus` (ward_daily), plus the scheduling scenarios above | `staffing_level` = short / surplus | `staffing_level`, `nurses_day_shift`, `nurses_night_shift`, `patients_per_nurse` | `short_staffing_share_by_season`, `relationship_short_staffing_cancellations`; admission-control policies with a nurse-ratio cap in Week 3 §6 |
| Reference mix [`baseline`] | `baseline` (ward_daily), `stays_baseline` (patient_stays) | unconditional | all columns | every family of the Week 3 report |

Where coverage is shown: the training support of every scenario is in the Week 1 report §1.2 (and
`GET /api/v1/scenarios?include_support=true`); generated rows, acceptance, strata TVD and fidelity
per scenario and model are in the Week 3 report §8; one validated dataset per scenario generated
through the API is listed in the Week 4 report §3. Calendar mode (`"mode": "calendar"`, ward_daily
only) returns one row per ward per date, so a scenario can also be laid over a date range.

## 7. Known limitations

The team documents these itself; examiners are likely to ask about them.

- The reference data is simulated because no real extract can be shared (Week 1 report §2); a
  facility would retrain on its own extract with the same schema (README "Limitations").
- Rows are conditionally independent: calendar mode does not model day-to-day census continuity, so
  multi-day bed-planning models get no carried-over census (README "Limitations"; DESIGN §1.1, §8.4,
  §13).
- The two tables are synthesised independently, with no linkage of stays to ward-days, and
  optimisation testing is defined for ward_daily only (README; DESIGN §1.1, §13).
- The allocation strata reproduce the training split's joint frequencies of their columns; this
  aggregate disclosure is reported but not scored (DESIGN §9.5, §13).
- Remaining measured quality gaps of the default models are listed in the Week 3 report §5-§7 and
  quantified in DESIGN §13; the run configuration is in the Week 3 report §1. The reported numbers
  come from one training run and one evaluation seed (42); for ward_daily `gc_tuned` the A/B
  evidence adds re-scores on three further evaluation seeds, on two of which one borderline check
  failed (DESIGN §7.2), and training-seed variation is not covered. The ward_daily spec was selected
  on the same evaluation, whose utility and privacy families use the holdout, so those figures carry
  some selection optimism (DESIGN §7.2). CTGAN and TVAE ran in one fixed, untuned configuration
  (DESIGN §7.5).
- The API has no authentication; by default it listens on 127.0.0.1 and its CORS policy admits only
  pages served from the same machine (Week 4 report §6; README "Using the API").
